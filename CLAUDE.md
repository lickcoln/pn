# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Goal

Official website for **Paranoid Noise**, a grunge/punk trio from Jakarta: a single-page React site (bio, members, a stompbox music player, gigs with RSVP, merch with WhatsApp checkout, a booking form). Source is `github.com/lickcoln/pn` (branch `main`), deployed on Vercel, with Supabase storing booking inquiries, ticket RSVPs, the shared site content edited in the admin portal, and the photos and MP3 songs uploaded there. **All website text is English** (the owner asked for it: UI, errors, admin portal, WhatsApp messages); only the band's own song titles stay Indonesian. Money is `IDR 65,000` (`formatIdr` in `src/lib/format.js`), admin timestamps use `en-GB`. `README.md` is still Indonesian and partly stale (it says Vite 6 and a repo named `paranoid-noise`); trust `package.json`.

## Commands

```bash
npm install
npm run dev       # Vite dev server, http://localhost:5173
npm run build     # vite build -> dist/ (what Vercel runs)
npm run preview   # serve dist/ locally
npm run lint      # oxlint, config in .oxlintrc.json
```

There is no test suite and no typecheck (plain JSX). Verify with `npm run build`, `npm run lint`, and the UI in `npm run dev`. Lint exits 0 with a small backlog of warnings (~12: setState-in-effect, exhaustive-deps); only new warnings or any error are regressions. Features here were verified with throwaway scripts kept outside the repo: headless Chrome over the DevTools protocol against a mock Supabase (auth, REST, Storage, a server that refuses or never answers, and a Realtime WebSocket server speaking the Phoenix protocol that supabase-js uses), two browsers at once for the live-update tests (an admin and a visitor), Node unit tests with a fake clock for `liveContent.js`, PGlite (WASM Postgres) for the RLS, storage and publication SQL, and a migration test that replays the real published content. Probing the real Realtime server from Node with the anon key is read-only and safe; never write to the production `site_content` for a test. When you change content handling, forms, the player or the admin, re-test those paths the same way instead of trusting the build.

## Environment and deploy

- Two env vars, both needed for Supabase: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. Locally they go in `.env.local` (gitignored; `.env.example` is the template). On Vercel they go in Project Settings -> Environment Variables. Vite inlines them at build time, so changing them on Vercel needs a redeploy.
- The production domain is `https://paranoidnoise.com` (bought at Hostinger, attached to the Vercel project; `www.` and plain `http://` redirect to it with a 308). `vite.config.js` fills the `__SITE_URL__` placeholders of `index.html` (canonical, `og:url`, `og:image`, `twitter:image`) with it for every build that runs on Vercel (`SITE_ORIGIN` constant); the optional env var `VITE_SITE_URL` overrides it, and a build outside Vercel keeps relative paths, which social crawlers ignore. The domain needs nothing in Supabase (password login, no email links; REST, Storage and Realtime accept any origin). The admin signs in again on a new domain because the session lives in that origin's localStorage.
- **Auto-deploy does not depend on the domain or on what is in the code:** every push to `main` is built and published by Vercel's GitHub integration. Content edited in the admin portal needs no deploy at all. Changing an environment variable in Vercel does need a manual Redeploy (Vite inlines it at build time).
- If the Supabase vars are missing, `isSupabaseConfigured` is false and the forms use localStorage, and the forms now say "not sent yet" (see Supabase below).
- Every push to `main` is a production deploy once Vercel is connected. `vercel.json` only sets `framework: vite` and an SPA rewrite to `/index.html`.

## Architecture

### Content: everything reads from `useBandData()`

- `src/data/bandData.js` holds the default content (members, singles, gigs, merch, contact, and `IMAGE_SLOTS`/`SITE_IMAGES`). Only `src/context/BandDataContext.jsx` imports it; components read `useBandData().config`. Keep it that way, or admin edits stop applying.
- The context layers saved content over those defaults and exposes the `update*` setters, all routed through `commit()`. `AdminPortal` (hidden; Ctrl+Shift+A, the footer's "Admin login" link on phones, or the faint lock icon bottom-right on large screens) edits the config and has JSON export/import and reset.
- **Two content modes**, chosen at runtime by `remoteStatus` in the context:
  - *Shared* (`'ready'`): once `supabase-admin.sql` has been run, the `site_content` row `main` (the whole config as JSON) is the source of truth for every visitor. Admin edits are upserted to it (debounced ~700 ms, admin session required). `pn_site_content_cache` in localStorage only gives returning visitors a fast first paint. "Reset" deletes the row, which returns the site to `bandData.js`.
  - *Local* (`'off'` / `'unavailable'`: no env vars, Supabase unreachable, or the table does not exist yet): admin edits are saved to `pn_live_band_config` in that browser only, and no other visitor sees them. `remoteReason` says why (`'missing'` or `'network'`); the admin login warns when the server cannot be reached instead of silently offering the local login.
- **Never write config to localStorage on load; only an admin edit may persist it.** Writing on mount froze every visitor's first-visit snapshot, which then won over the defaults and hid later deploys of `bandData.js`.
- **Live updates: an open page follows what the admin publishes, without a reload** (`src/lib/liveContent.js`, wired in `BandDataContext`; only in shared mode, `remoteStatus === 'ready'`). The channel is `postgres_changes` on `site_content` through `subscribeToSiteContent` in `supabase.js`, with two bindings (`*` filtered to `id=eq.main`, and a separate unfiltered `DELETE` one, because the server cannot filter deletions) and **`postgres_changes_options: { wait: true }`**, which makes the server refuse the join when the table is not enabled for Realtime. Without `wait` it accepts the join silently and never sends anything, which would make "live" a lie. The pushed message carries the whole config (a few KB); an incomplete or errored message just triggers a normal fetch. Around it:
  - a safety net that needs no setup: a tiny `select=updated_at` request every 120 s while live and every 30 s when not (and on returning to the tab, `online`, and a bfcache restore); only a different version downloads the content;
  - a tab hidden for 2 minutes gives its connection back (free plan: 200 at once) and takes it again on return; a server refusal (`RealtimeDisabledForConfiguration` / "Unable to subscribe to changes") is final for that page and leaves it on the 30 s checks, with a console hint;
  - the page that loaded while the server was unreachable keeps retrying quietly (8 s, 16 s, ... up to 60 s) instead of staying on stale content, except an admin in the local-only login;
  - `versionRef` is the published version (`updated_at` as ms) the page shows; equal versions are ignored (the admin's own save coming back), so ordering never depends on clocks. `dirtyRef` is true from an admin edit until it is saved: while it is, content arriving from the server is ignored, otherwise a change from another device would wipe an unsaved edit (the later save wins, as before);
  - `liveStatus` (`live` / `polling` / `connecting` / `off`) and `liveEcho` (`confirmed` / `missing`: did the admin's own save come back through the live connection within 6 s) are shown in the admin portal's sync banner, so a broken setup is visible to the owner instead of silent. `supabase-realtime.sql` publishes the table; on the owner's project it was already enabled (checked against the real server: `site_content` joined with `wait`, an unpublished table was refused).
  - `liveContent.js` has no imports on purpose (the server calls are injected), so its timing can be unit-tested with a fake clock. Do not replace the server push with Broadcast: any visitor could send those messages.
- **Saved content is untrusted JSON.** `mergeConfig` ends in `sanitizeConfig` (`src/lib/sanitizeConfig.js`): lists that are not lists fall back to the defaults, entries get ids, text fields become strings, prices become numbers (`"Rp 185.000"` -> 185000; rupiah has no cents), empty pictures fall back to the logo, a broken WhatsApp number or email falls back to the default, and `priceFormatted` is always derived from `price`. Every section is also wrapped in its own `ErrorBoundary` (and the whole app in a page-level one), so one bad value cannot blank the site. Components may therefore assume the shapes `sanitizeConfig` guarantees (for example `merch[].sizes` is a non-empty array).
- **A saved snapshot shadows the defaults, so changing default copy or default photos in `bandData.js` does not reach a site that already has saved content.** `src/lib/contentMigration.js` handles that (`CONTENT_VERSION` is 3): `mergeConfig` runs `migrateLegacyContent`, which swaps every saved item that still matches an old default, the saved bio if it is an old default text, and the photo slots that still point at an old default path, for the current defaults, and keeps anything the admin edited. To change defaults again: compute the fingerprint (`fingerprint()`, stable JSON + FNV-1a) of every item that will change *before* editing `bandData.js`, append it to the item's list in `LEGACY_FINGERPRINTS` (and to `LEGACY_BIO` / `LEGACY_IMAGES` where relevant), and bump `CONTENT_VERSION`. Replay the real published content through the migration afterwards. Otherwise tell the user to change it in the admin portal.
- **Images.** Site-wide images live in `config.images` (one entry per `IMAGE_SLOTS` item: logo, hero and music-section backgrounds, lineup/profile photos, press kit); a member's `image`, a single's `coverArt`, and a merch item's `image` live on the item. Components must read them from `config`, never hardcode `/band/...` paths. The browser tab icon follows `images.logo`. Defaults are files in `public/` (`/band/`, `/images/`, `/singles/`). The big default band photos are WebP (`*.webp`, about 15% of the PNG size); the PNG originals stay in `public/` because saved snapshots may still point at them, and the press kit default stays a PNG because visitors download it. Convert new large photos to WebP before adding them to `public/`. `<img>` tags below the first screen use `loading="lazy"`; the hero background has `fetchPriority="high"`. The link-preview picture is the static `public/og-image.jpg` (1200x630); it cannot follow the admin.
- A single's `audioUrl` (+ `audioName`) is its uploaded MP3; without one the player falls back to the synthesized riff preview (`riffType`).
- **Gigs** (`src/lib/gigs.js`). Dates are free-text English strings like `'24 OCTOBER 2026'`, but `parseGigDate` also reads Indonesian months, ISO, `d/m/yyyy` and ranges (`24-25 NOVEMBER 2026`). The public list shows upcoming shows soonest first and moves a show to "Past shows" the day after it happened (today means today in Jakarta), or at once when its category is `Past Gig`. A date that cannot be read is shown as typed and never becomes past by itself; the admin form says how the date is read. A show is sold out when its status or price says "Sold Out". The hero button plays `config.singles[0]`, and the admin can reorder singles.
- Theme: `THEME_PRESETS` (in the context) sets CSS vars `--primary-rock*` on `<html>`. Preset class strings (`accentText`, `accentBg`, ...) must stay literal Tailwind class names; Tailwind v4 only emits classes it finds as whole strings in source, so never build them by concatenation.

### Supabase

- `src/lib/supabase.js` holds every Supabase call. Visitors only insert: `submitBookingInquiry` -> `booking_inquiries`, `submitTicketRsvp` -> `ticket_rsvps`. Each returns `{ mode }`: `'supabase'` means the band can see it; on any error or after 15 s without an answer the data is kept in localStorage (`pn_bookings`, `pn_rsvps`) and `mode` is `'local'` or `'memory'`. **The forms only say "sent" for `'supabase'`**; otherwise they say "NOT SENT YET" and offer the WhatsApp button with the details filled in (`FormResult`). Look for "falling back to local" in the browser console.
- The schema is four SQL files, applied by hand in the Supabase SQL Editor in this order (no migration tooling): `supabase-schema.sql` (tables + anon INSERT; not re-runnable), `supabase-admin.sql` (opt-in, re-runnable: `site_content`, `is_admin()`, admin-only reads, the commented steps to create the admin user), `supabase-media.sql` (opt-in, re-runnable: the `site-media` storage bucket) and `supabase-realtime.sql` (opt-in, re-runnable: adds only `site_content` to the `supabase_realtime` publication so changes are pushed to open pages; never add the booking or RSVP tables). Until the second one is run the site works in local mode; until the third, uploads fail with an error telling the admin to run it; without the fourth, pages still catch up through the 30 s checks. RLS is on everywhere. Rules:
  - Never chain `.select()` onto visitor inserts. RETURNING needs a SELECT policy, so RLS rejects the insert (error 42501) and it falls back to localStorage. This is why they have no `.select()`.
  - Never add an `anon` SELECT policy on `booking_inquiries` / `ticket_rsvps`: they hold visitors' names, emails and phone numbers. Only the admin reads them.
  - Admin means `app_metadata.role = 'admin'` in the JWT (`public.is_admin()`), granted server-side with SQL. Never base a policy on `user_metadata` (users can edit it) or on `authenticated` alone (sign-ups can be enabled).
  - The form insert policies cover `anon, authenticated`, so the forms keep saving while the admin is signed in on the same browser.
  - Payload keys must match the column names exactly (snake_case; built in `ContactBooking.jsx` and `EventSchedule.jsx`).
  - Any schema change must be mirrored into the SQL files and applied by the user in the dashboard.
- **Storage.** `uploadMedia(folder, file)` puts photos and MP3s in the public `site-media` bucket (anyone downloads, only the admin uploads/replaces/deletes; 25 MB limit; jpeg/png/webp/gif/mp3 only, no SVG because it can carry scripts). Each upload gets a new name, so replaced files never show from cache. The storage client sends a `File` with the type the browser detected and ignores the `contentType` option, so `uploadMedia` rewraps MP3s as `audio/mpeg` (some browsers report `audio/mp3` or nothing). `MediaField` shrinks photos (`prepareImage`) before upload and the replaced file is deleted ~12 s later (`discardOldMedia` in `AdminPortal`), only if nothing in the saved content still points to it. Free plan: 1 GB storage, 5 GB downloads a month.
- Bookings and RSVPs are read in the admin portal's "Booking Requests" / "Ticket RSVPs" tabs in shared mode, or in the Supabase Table Editor. In local mode those tabs show only the localStorage fallback.

### Contact and links

- `contact.whatsappRaw` is the **only** stored phone number; it is normalised to digits with the country code (`0812...` -> `62812...`). The text visitors read (`+62 812-9999-0099`) and every `wa.me` link are derived from it (`formatWhatsApp`, `whatsappLink` in `src/lib/contactInfo.js`). `contact.whatsappDisplay` in old saved content is unused. Use `whatsappLink`, never build a `wa.me` URL by hand.
- Social links go through `socialChannels(contact)`: a channel with an empty URL is hidden in the footer, the contact section and the phone menu, and `externalUrl` adds `https://` when it is missing and drops any other scheme (`javascript:`). The text under a channel name comes from `contact.<channel>Handle`. The same `externalUrl` guards the single's platform buttons and the gig map link.
- No payment backend. The cart lives in `App.jsx` (`localStorage['pn_cart']`, read defensively, and reconciled with the catalog after content loads so a WhatsApp order never carries an old price or a removed product), and checkout is a `wa.me` message.

### Player, audio, mobile

- `src/utils/audioSynth.js` exports a singleton `audioEngine`. One chain serves both sources: riff voices (oscillators -> always-on amp distortion -> cab filter) and the MP3 `<audio>` element (`crossOrigin = 'anonymous'`, which the storage server allows; without CORS the Web Audio graph would be silent) both go through the pedal (gain curve + tone lowpass), a three-band equalizer (bass shelf 120 Hz, mid peak 1 kHz, treble shelf 6 kHz, 50% = flat, +/-12 dB), the analyser, the master level and a limiter. Every setting is a 0-100 percentage (`setSetting`/`setSettings`; stored until the context exists, because browsers only create it from a click). `playSong` resumes a paused song, `playTrackRiff` is the fallback for a single without an MP3.
- The pedal starts **bypassed** (App's `distortionActive` is false) so real songs sound like the recording; GAIN and TONE only act while it is engaged. Sliders in `DiscographyPlayer` pair a range input with a typed percentage box, and are remembered (validated) in `localStorage['pn_player_settings']`.
- In `DiscographyPlayer`, `startTrack` always plays and `togglePlay` is for buttons. The current track is derived from `currentId` and the singles list on every render (an edited or deleted single never leaves the console pointing at stale data). The hero's play button passes a fresh `playRequest` object each press so it works again after a pause. The visualizer animates only while on screen. The analyser is only 64 points wide, so its bins cannot show bass; a test that measures it must set `smoothingTimeConstant = 0`, because the analyser smooths per call and the visualizer is no longer calling it every frame.
- The hero's stompbox logo toggles a looping riff and stops it by itself after 8 s.
- **Phone layout.** `MobileNav` is a fixed bottom tab bar below `lg` (7 sections, the one crossing the middle of the screen is highlighted). Its back-to-top button only appears while the visitor scrolls back up. The floating admin lock is hidden below `lg`; phones use the footer's "Admin login" link (`OPEN_ADMIN_EVENT`). Anything fixed at the bottom has to clear the bar: `App.jsx` adds `pb-16`. Singles are compact rows below `sm` and cover cards above it, the equalizer sliders fold behind a button below `md`, the shop is two columns, members sit beside their photo. Fields are 16 px on touch screens (`@media (pointer: coarse)` in `index.css`) so iPhones do not zoom in. `prefers-reduced-motion` is honoured (CSS and `MotionConfig`). When you add a section, check it at 390 px width; the whole page is about 16 screens tall there.
- Popups (RSVP, cart, admin login) use `useModal` (Escape closes, the page behind stops scrolling) and scroll inside themselves on short screens. The big admin panel deliberately ignores Escape.

### Admin portal

- `src/components/AdminPortal.jsx` is the shell (login, header, sync banner, sidebar); each tab is a component in `src/components/admin/` (`GigsTab`, `MerchTab`, `SinglesTab`, `ContactTab`, `MembersTab`, `BioTab`, `ThemeTab`, `ImagesTab`, `InboxTab`, `BackupTab`; shared inputs in `ui.jsx`). A tab owns its unsaved draft and receives `onSave(value, message)`. All tabs stay mounted (hidden when inactive) so switching tabs never loses typing, and a tab is remounted with `key={JSON.stringify(slice)}` only when the saved data it edits changes. Do not move drafts back into the shell: an autosave in one tab used to wipe unsaved text in all the others.
- Gigs and merchandise are edited one item at a time with explicit Save buttons (a photo uploaded in a form is saved with the form). Members and singles are whole-list drafts; uploads there save the whole draft at once. Singles need a title before anything is published. Deleting or replacing a file schedules `discardOldMedia`.
- `AdminPortal` has two logins. In shared mode it is Supabase Auth (email + password), and an account without `app_metadata.role = 'admin'` is signed out again (sign-out is `scope: 'local'`, so signing out on the PC keeps the phone signed in). In local mode it is a client-side comparison against credentials hardcoded in `AdminPortal.jsx` (session flag in `sessionStorage['pn_admin_session']`); those ship in the public bundle and repo, so local mode is a UI gate only and that password must never be reused for the Supabase admin account. Uploads need the shared mode and an admin session.
- Styling is Tailwind v4 via `@tailwindcss/vite` with no `tailwind.config`; custom utilities (`font-bebas`, `glow-red`, glitch effects, the `pn-range` slider) live in `src/index.css`. Unlayered CSS there beats utility classes, which is how the 16 px fields rule works.
- The `*.cjs` files in the repo root are one-off PDF/image extraction scripts (Node built-ins only). They hardcode an absolute path to a PDF on the original author's machine and are not part of the build; their output is already in `public/`. Many files in `public/images/` and `public/singles/` are duplicates of each other, kept because older saved content may still point at them; do not delete any without checking the published content.

## Working rules

- Band-owned facts (member info, bio, single titles/dates/links, gig dates/venues/prices/status, merch, phone/WhatsApp, social URLs, copy, photos) come from the user. Do not invent, "correct" or fill in placeholders; ask. The band bio's spelling mistakes were fixed with the owner's approval (content version 3). Still unverified and probably placeholders: the WhatsApp number `+62 812-9999-0099`, the YouTube and Spotify artist links (the YouTube handle returned 404, the Spotify artist id is not a real id), the merch descriptions and stock labels, and the product photos (the cap shows a member portrait, the pin pack the logo). Flag them instead of silently changing them.
- Keep every user-visible string English, including new admin text, error messages and WhatsApp templates.
- Sources of truth: `package.json` (versions, scripts), the three `supabase-*.sql` files (database), `.env.example` (env var names). If a task touches RLS/schema, the persistence model, or admin auth, confirm the intended behaviour with the user before coding. There is no way to run SQL against their project from here, so SQL changes must be handed over as a script with the steps to run it.
